## 1. Установка, запуск и транспорт OpenCodeService

Класс `OpenCodeService` управляет жизненным циклом бинарника OpenCode CLI, сохранением конфигурации, генерацией криптографических токенов и локальным шлюзовым интерфейсом HTTP/Unix-сокет (`desktop/opencode-service.cjs`).

### Инициализация и конфигурация сервиса
Сервис инициализируется в заданной корневой папке (`root`), проверяя или создавая безопасные права доступа к каталогу (`0o700`) и загружая настройки из `connection.json` [desktop/opencode-service.cjs:54-76](). Он проверяет, что настроенные пути проектов не пересекаются с чувствительными каталогами хоста или системными корнями, используя проверки `projectPath` [desktop/opencode-service.cjs:18-25]().

Аутентификация строится на случайном hex-токене длиной 32 байта и пароле, который хранится в `server-key` с ограниченными правами `0o600` [desktop/opencode-service.cjs:72-76]().

### Транспорт и маршрутизация шлюза
В зависимости от платформы хоста сервис предоставляет API-шлюз либо через Unix domain socket (`api.sock`), либо через локальный TCP-порт (`windowsPort`) [desktop/opencode-service.cjs:79](). Запросы требуют HTTP Basic Authentication с именем пользователя `opencode` и сгенерированным паролем [desktop/opencode-tasks.cjs:10-28]().

## 2. Режимы изоляции: песочница и KVM

Экземпляры OpenCode работают в строгих режимах изоляции: `sandbox` (с Bubblewrap на Linux) или `kvm`. 

### Аргументы песочницы Bubblewrap
Функция `sandboxArgv` формирует строгие аргументы изоляции для Bubblewrap (`bwrap`) [desktop/opencode-service.cjs:26-46]():
- `--unshare-all`: изоляция пространств имён (user, mount, PID, IPC, network, uts).
- `--clearenv`: очищает все унаследованные переменные окружения.
- `--cap-drop ALL`: сбрасывает все Linux capabilities.
- `--ro-bind` / `--bind`: монтирует только необходимые системные пути (`/usr`, `/bin`, `/lib`, `/proc`, `/dev`, `/tmp`) и явно разрешённые каталоги проектов [desktop/opencode-service.cjs:26-36]().
- внедрение IPC-токена хост-сервисов и конфигурации MCP, когда включены `hostServices` [desktop/opencode-service.cjs:37-42]().

## 3. Состояния задач OpenCodeTasks и маршрутизация шлюза

Класс `OpenCodeTasks` на стороне Node (`desktop/opencode-tasks.cjs`) обрабатывает входящие запросы на выполнение (`start`, `status`, `cancel`, `answer`) и координирует выполнение задач с бэкендом `OpenCodeService`.

### Действия над задачами и жизненный цикл
- **`start`**: проверяет разрешения на проекты, создаёт или находит экземпляры сервиса, создаёт удалённую сессию OpenCode через `POST /api/session` и отправляет начальный целевой промпт через `POST /api/session/{id}/prompt` [desktop/opencode-tasks.cjs:52-94]().
- **`status`**: агрегирует метаданные сессии, активные состояния, формы, разрешения и журнал сообщений ассистента с сервера OpenCode [desktop/opencode-tasks.cjs:95-116]().
- **`cancel`**: отправляет запрос на прерывание (`POST /api/session/{id}/interrupt?resume=false`), чтобы остановить выполнение без возобновления [desktop/opencode-tasks.cjs:44-47]().

## 4. Формы, разрешения и ответы пользователя

Интерактивные формы и разрешения на инструменты, запрашиваемые сессиями OpenCode, безопасно передаются через контроллер задач без участия модели [desktop/tests/opencode-tasks.test.cjs:60-69]().

### Передача и обработка форм
Когда OpenCode публикует форму через `GET /api/session/{id}/form`, `OpenCodeTasks` показывает эти поля ввода в полезной нагрузке статуса [desktop/opencode-tasks.cjs:97-101](). Когда пользователь отправляет ответ (`action: answer`), ответ доставляется напрямую к конкретному идентификатору запроса формы в сессии OpenCode [desktop/opencode-tasks.cjs:48](), [desktop/tests/opencode-tasks.test.cjs:60-69]().

## 5. Делегирование на стороне Python (`factory/core/opencode_tasks.py`)

Python-часть (`factory/core/opencode_tasks.py`) реализует инструмент `opencode_task`, зарегистрированный в реестре агента [factory/core/opencode_tasks.py:17-30](). Она взаимодействует с десктопным окружением через `DesktopBrowserPipe` и хранит долговременное состояние в локальной базе SQLite (`tasks.sqlite3`) [factory/core/opencode_tasks.py:28-36]().

### Схема базы данных и восстановление после сбоев
База данных хранит запуски по следующей схеме [factory/core/opencode_tasks.py:37-45]():
```sql
CREATE TABLE IF NOT EXISTS runs (
    id TEXT PRIMARY KEY,
    request_key TEXT UNIQUE,
    state TEXT,
    document TEXT
)
```
При инициализации все незавершённые задачи (`state NOT IN FINAL`) помечаются как `interrupted` из-за перезапуска приложения [factory/core/opencode_tasks.py:40-45]().
