## Purpose and Scope

This page documents the background processing architecture of the Igorek-Harness Python core and desktop integration. It covers how background queue consumers are executed, how worker presence and leases are maintained via file locking, how scheduled tasks are evaluated and triggered, how the agent runtime mutex prevents concurrent execution races, and how stuck tasks are cleaned up.

Sources: `factory/core/worker.py`, `factory/core/scheduler.py`, `factory/core/worker_presence.py`, `desktop/agent_runtime.py`

## Background Workers and Execution Loop

The background worker subsystem is driven by the `Worker` class [factory/core/worker.py:3-5] which polls database-backed task queues and executes them using configured model backends (such as Claude or Codex).

When a worker initializes, it sets up profile configurations, resolves tools via `get_tool_schemas()` [factory/core/worker.py:32], establishes MCP capabilities [factory/core/worker.py:60-66], and enters a polling loop. Tasks are pulled from the SQLite database, validated against security levels [factory/core/worker.py:174-189], and executed under isolated conditions where applicable.

Sources: `factory/core/worker.py`

## Worker Presence and Leases

To advertise live queue consumers without altering execution policies, the harness utilizes `WorkerPresence` and consumer checks located in `factory/core/worker_presence.py`. 

Workers write temporary JSON state files inside a private profile directory (`run/cli/<identity>/workers/`) and acquire an exclusive file lock (`.lock`) on them. Other components check these presence files to verify whether a queue consumer is active and configured correctly.

## Task Scheduler and Timezones

Scheduled tasks are managed by the `Schedule` class and supporting functions in `factory/core/scheduler.py`. The scheduler supports multiple schedule types including `'daily'`, `'hourly'`, and `'once'` [factory/core/scheduler.py:84-167], running entirely on built-in Python modules with SQLite backing.

Each `Schedule` instance parses its schedule configuration, calculates next execution timestamps via `calculate_next_run()` [factory/core/scheduler.py:77-167], handles timezone conversions using `zoneinfo` or UTC fallbacks, and tracks execution history (`run_count`, `last_run_at`, `last_output`) [factory/core/scheduler.py:35-75].

Sources: `factory/core/scheduler.py`

## Agent Runtime Mutex and Lifecycle

In desktop environments, `DesktopAgentRuntime` [desktop/agent_runtime.py:24-140] manages a standard queue worker bound to an unlocked vault. It enforces concurrency constraints via threading primitives:

1. `execution_lock` (`threading.Lock()`): Ensures that only one task execution runs at a time. If an agent is busy, attempts to stop or overlap execution raise `AgentBusyError` [desktop/agent_runtime.py:12, 161].
2. `control_lock` (`threading.RLock()`): Synchronizes thread start and stop control flows across the runtime.

## Stuck Task Cleanup and Error Recovery

Background workers and schedulers incorporate recovery mechanisms to deal with interrupted operations:
- When a worker encounters unhandled exceptions or when a desktop runtime is stopped forcefully, `stop_event` signals the worker thread to break out of its active poll loop [desktop/agent_runtime.py:123-127].
- Isolation managers and terminal contexts are closed cleanly in `finally` blocks to prevent orphaned sandboxed processes or leaked locks [desktop/agent_runtime.py:128-131].
- Presence lease files and associated `.lock` descriptors are unlinked automatically upon exit via `WorkerPresence.__exit__()` [factory/core/worker_presence.py:93-96], ensuring crashed workers do not permanently block profile concurrency checks.

Sources: `factory/core/worker.py`, `desktop/agent_runtime.py`, `factory/core/worker_presence.py`
