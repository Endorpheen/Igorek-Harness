## 1. OpenCodeService Installation, Launch, and Transport

The `OpenCodeService` class manages the lifecycle of the OpenCode CLI binary, configuration persistence, cryptographic token generation, and the local HTTP/Unix-socket gateway interface (`desktop/opencode-service.cjs`).

### Service Initialization and Configuration
The service initializes within a designated root folder (`root`), verifying or creating secure directory permissions (`0o700`) and loading `connection.json` settings [desktop/opencode-service.cjs:54-76](). It validates that configured project paths do not overlap with sensitive host directories or system roots using `projectPath` checks [desktop/opencode-service.cjs:18-25]().

Authentication is enforced via a random 32-byte hex token and a password stored in `server-key` with restricted `0o600` permissions [desktop/opencode-service.cjs:72-76]().

### Transport and Gateway Routing
Depending on the host platform, the service exposes an API gateway either via a Unix domain socket (`api.sock`) or a local TCP port (`windowsPort`) [desktop/opencode-service.cjs:79](). Requests require HTTP Basic Authentication using the `opencode` username and the generated password [desktop/opencode-tasks.cjs:10-28]().

## 2. Sandbox vs KVM Isolation Modes

OpenCode instances run under strict isolation modes: `sandbox` (using Bubblewrap on Linux) or `kvm`. 

### Bubblewrap Sandbox Arguments
The `sandboxArgv` function builds the strict isolation arguments for Bubblewrap (`bwrap`) [desktop/opencode-service.cjs:26-46]():
- `--unshare-all`: Namespaces isolation (user, mount, PID, IPC, network, uts).
- `--clearenv`: Clears all inherited environment variables.
- `--cap-drop ALL`: Drops all Linux capabilities.
- `--ro-bind` / `--bind`: Mounts only required system paths (`/usr`, `/bin`, `/lib`, `/proc`, `/dev`, `/tmp`) and explicitly permitted project directories [desktop/opencode-service.cjs:26-36]().
- Host services IPC token and MCP configuration injection when `hostServices` are enabled [desktop/opencode-service.cjs:37-42]().

## 3. OpenCodeTasks Job States and Gateway Routing

The `OpenCodeTasks` class on the Node side (`desktop/opencode-tasks.cjs`) handles incoming execution requests (`start`, `status`, `cancel`, `answer`) and coordinates task execution against the `OpenCodeService` backend.

### Job Actions and Lifecycle
- **`start`**: Validates project grants, creates or retrieves service instances, creates a remote OpenCode session via `POST /api/session`, and dispatches the initial goal prompt via `POST /api/session/{id}/prompt` [desktop/opencode-tasks.cjs:52-94]().
- **`status`**: Aggregates session metadata, active states, forms, permissions, and assistant message logs from the OpenCode server [desktop/opencode-tasks.cjs:95-116]().
- **`cancel`**: Sends an interrupt request (`POST /api/session/{id}/interrupt?resume=false`) to halt execution without resuming [desktop/opencode-tasks.cjs:44-47]().

## 4. Forms, Permissions, and User Answers

Interactive forms and tool permissions requested by OpenCode sessions are relayed securely through the task controller without model mediation [desktop/tests/opencode-tasks.test.cjs:60-69]().

### Form Relaying and Answering
When OpenCode exposes a form via `GET /api/session/{id}/form`, `OpenCodeTasks` surfaces these inputs in its status payload [desktop/opencode-tasks.cjs:97-101](). When the user submits an answer (`action: answer`), the response is dispatched directly to the exact form request identifier on the OpenCode session [desktop/opencode-tasks.cjs:48](), [desktop/tests/opencode-tasks.test.cjs:60-69]().

## 5. Python-Side Delegation (`factory/core/opencode_tasks.py`)

The Python counterpart (`factory/core/opencode_tasks.py`) implements the `opencode_task` tool registered in the agent registry [factory/core/opencode_tasks.py:17-30](). It interfaces with the desktop environment via `DesktopBrowserPipe` and maintains durable state in a local SQLite database (`tasks.sqlite3`) [factory/core/opencode_tasks.py:28-36]().

### Database Schema and Crash Recovery
The database stores runs using the following schema [factory/core/opencode_tasks.py:37-45]():
```sql
CREATE TABLE IF NOT EXISTS runs (
    id TEXT PRIMARY KEY,
    request_key TEXT UNIQUE,
    state TEXT,
    document TEXT
)
```
Upon initialization, any uncompleted tasks (`state NOT IN FINAL`) are marked as `interrupted` due to application restart [factory/core/opencode_tasks.py:40-45]().
