## Purpose and Scope
This section covers the technical architecture and execution flow for Igorek's release update subsystem. This includes the update check, download, and cryptographic verification pipeline (`desktop/release-updates.cjs`), interactive desktop update dialogs (`desktop/release-updates-ui.cjs`), post-exit background installation helpers (`desktop/release-install.cjs` and `desktop/release-install.py`), release notes assets (`desktop/assets/release-notes.json`), the "What's New" UI, and the in-app navigation history controller (`factory/web_ui/static/app-history.js`).

---

## 1. Release Updates Architecture & Flow
The release update mechanism queries GitHub releases, validates target architecture and OS assets, enforces strict redirect policies, and performs cryptographic verification of downloaded payloads before staging them for installation.

The `ReleaseUpdates` class manages version comparison and asset matching (`desktop/tests/release-updates.test.cjs`). It ensures that downloads only occur over safe redirect URLs (`allowedRedirect`) and omits sensitive headers/credentials during public release checks (`desktop/tests/release-updates.test.cjs`).

## 2. Interactive Update Dialog & Progress Presentation
The desktop UI orchestrates the update lifecycle via `updateDialog` (`desktop/release-updates-ui.cjs`). It coordinates with the Electron main window to display progress bars, handle user prompts, and map low-level errors to localized user-facing messages.

### Key Functions and Error Handling
* `updateDialog({app, dialog, shell, current, portable, install, channel, fetch, presentationFactory})`: Defines an async closure that guards against concurrent update attempts, prompts the user to download or view releases, updates progress via `parent.setProgressBar()`, and executes the installer callback upon confirmation [desktop/release-updates-ui.cjs:4-63]().
* Error Translation: Maps specific exceptions like `update_tasks_active`, `update_opencode_active`, `update_locked`, and `unverified_release_asset` to descriptive dialog boxes [desktop/release-updates-ui.cjs:46-60]().

Sources: [desktop/release-updates-ui.cjs:1-64]()

## 3. Background Installation & Platform Helpers
Once an update binary is downloaded and cryptographically verified, the desktop application exits and hands execution over to a detached Python installation helper script (`desktop/release-install.py`) spawned via `launchInstallation` (`desktop/release-install.cjs`).

```mermaid

    subgraph "Python Helper Process"
```

### Installation Subsystem Components
* `installationTarget()`: Resolves the active installation directory depending on the platform (`win32` vs Linux AppImage or user snapshot installation) [desktop/release-install.cjs:14-33]().
* `launchInstallation()`: Writes a secure installation request JSON file (`install-request-{attempt}.json`), copies `release-install.py` into the cache directory, sets up restricted Windows Python execution environments if necessary, and spawns the detached helper process before calling `app.quit()` [desktop/release-install.cjs:35-71]().
* `read_request()` & `verified_file()`: Validates file existence, size bounds, SHA-256 integrity, and process ownership rules in `desktop/release-install.py` [desktop/release-install.py:19-56]().
* `close_inherited_installation_lock()`: Safely closes inherited file descriptors matching `run.lock` on Linux without releasing the active launcher's lock prematurely [desktop/release-install.py:59-76]().
* `wait_for_exit()`: Monitors the parent process PID using Windows `OpenProcess`/`WaitForSingleObject` or Linux `os.kill(pid, 0)` polling until the desktop harness fully terminates [desktop/release-install.py:78-104]().
* `replace_appimage()` & `install_snapshot()`: Handles atomic replacement of AppImages with rollback backups or unpacks `.deb` archives for user snapshots [desktop/release-install.py:106-155]().

Sources: [desktop/release-install.cjs:1-86](), [desktop/release-install.py:1-155](), [tests/test_release_install.py:1-113]()

## 4. Release Notes Assets & "What's New" UI
Release metadata and changelogs are bundled as JSON assets and surfaced through dedicated Electron windows when users launch an updated version.

* Release Notes Structure: `desktop/assets/release-notes.json` contains the current release version, an array of localized change strings, and the update channel (`desktop/assets/release-notes.json:1-9`).
* Preload and IPC: `desktop/whats-new-preload.cjs` exposes the `IgorekWhatsNew` bridge, which communicates over the `igorek:whats-new` IPC channel to read change lists and update persistence preferences (`desktop/whats-new-preload.cjs:1-3`).
* Styles & Markup: `desktop/whats-new.html` and `desktop/whats-new.css` provide a clean, CSP-restricted dialog interface for displaying version highlights [desktop/whats-new.html:1-14]().

Sources: [desktop/assets/release-notes.json:1-9](), [desktop/whats-new.html:1-14](), [desktop/whats-new-preload.cjs:1-2]()

## 5. In-App Navigation History
The front-end state machine includes a robust history management class (`factory/web_ui/static/app-history.js`) that tracks views, active chat sessions, and side panels without relying on traditional browser URL mutations [desktop/tests/app-history.test.cjs:4-10]().

### History Operations
* `record(route)`: Clones mutable route inputs, validates against unsafe schemas (such as `javascript:` URIs or directory traversal patterns like `../`), bounds history length, and truncates forward branches when navigating to a new view after going back [desktop/tests/app-history.test.cjs:11-20]().
* `back()` / `forward()`: Restores previous or subsequent view configurations asynchronously while ensuring failed restores do not corrupt the navigation index [desktop/tests/app-history.test.cjs:21-26]().

Sources: [desktop/tests/app-history.test.cjs:1-26]()
