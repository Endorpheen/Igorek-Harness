# OpenCodeService and Task Lifecycle

## Current lifecycle · 0.2.12

`OpenCodeService` still installs the pinned official OpenCode 2.0.27 binary with SHA-512 verification and starts a separate service using the selected original project. `OpenCodeTasks.start()` requires `execution_mode: 'direct'`, a granted Git directory and an available verified model profile. Copy-mode requests are rejected. The exact assignment session opens on the right; the initial request returns a `run_id` without waiting for completion.

The model-facing schema permits only `start` and `status`. A forced `cancel` is rejected with `opencode_observation_read_only` in both the Python tool handler and Electron controller, without sending an interrupt. The bridge's `answer` operation is reserved for exact owner input routing and is not a model tool action. The owner can stop work in the native OpenCode interface.

Active `status` requests refresh the same session through GET calls. Python and the existing monitor share the same ingestion path, so an explicit read neither swallows nor duplicates automatic messages or cards. Missing `run_id` selects only the originating chat's active or most recent assignment. Terminal receipts require no new live request.

The additional `progress` object contains `observed_at`, `session_active`, `latest_message`, `recent_actions`, `active_actions`, `action_counts` and truncation flags. Python adds `available`, `age_seconds`, `freshness` and bounded pending owner input previews. Freshness is `live`, `stale`, `historical` or `unavailable`. Public text is bounded to 4,000 characters and action lists to ten entries. Shell commands, raw inputs/outputs and private reasoning are not forwarded; recognized secrets are redacted.

The durable SQLite receipt, stable request key, exact owner form replies and restart recovery remain. An observed owner interruption closes expired cards and releases the write guard without answering or interrupting OpenCode. Completion queues one result turn after the main chat becomes idle. Existing edits remain in the original project; there is no transfer stage or automatic rollback.
