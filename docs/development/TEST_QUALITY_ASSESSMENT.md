# Risk-based testing assessment

This is a historical assessment. For the current methodology, see [Testing methodology](TESTING_METHODOLOGY.md).

## Evidence and principles

* [Google: Code Coverage Best Practices](https://testing.googleblog.com/2020/08/code-coverage-best-practices.html): use coverage to locate neglected behavior; execution of a line is not proof of a useful assertion. Once the agreed 90% line-coverage milestone is reached, keep recording coverage but do not add low-value cases merely to raise it.
* [Google: Mutation Testing](https://testing.googleblog.com/2021/04/mutation-testing.html): introduce plausible faults in isolated copies, run the relevant tests against the original and mutants, and investigate survivors. Exclude or separately classify equivalent, invalid, timed-out and irrelevant mutants; do not claim that one score proves correctness.
* [Microsoft: Architecture strategies for testing](https://learn.microsoft.com/en-us/azure/well-architected/operational-excellence/testing): choose tests and acceptance criteria based on user impact and risk rather than one template for every component.
* [Meta: LLM-powered bug catchers](https://engineering.fb.com/2025/02/05/security/revolutionizing-software-testing-llm-powered-bug-catchers-meta-ach/): define a failure class first, then use model-generated tests and realistic mutants; independently execute and review them. We do not claim to have implemented Meta's ACH system.
* [Google: Larger Testing](https://abseil.io/resources/swe-book/html/ch14.html): complement unit tests with realistic multi-component paths; explicitly identify synthetic providers and other doubles because their behavior may differ from real dependencies.
* [AWS: Failure injection and resilience](https://docs.aws.amazon.com/wellarchitected/latest/reliability-pillar/rel_testing_resiliency_failure_injection_resiliency.html): define expected behavior and stop conditions, inject faults in disposable resources, observe recovery and retain reproducible checks. Never disrupt the user's active runtime, model server or data.

## Priorities and measurements

1. **Conversation and task data:** verify concurrent appends, metadata updates, crash boundaries and repeat delivery; measure preservation, no unintended duplicates, recovery and bounded completion. Use real processes and temporary data when feasible.
2. **Security boundaries:** test paths escaping approved roots, symlink swaps, permission denial, unauthorized tool requests and secret leakage; distinguish mocked unit tests from platform-native isolation checks.
3. **Agent workflows:** cover submission, provider/tool execution, cancellation, reconnection and resumed delivery end to end with a synthetic provider, then separately document what requires actual desktop, Android, model or Windows environments.
4. **Mutation pilot:** select high-risk changes in history, access control and recovery. Record each mutant, affected tests, original pass, mutant result and classification; inspect survivors rather than optimize the aggregate alone.
5. **Flakiness and hangs:** repeat selected time-sensitive and concurrent tests in isolated runs; record repetitions, failures, duration and diagnostic evidence. A clean sample cannot prove absence of races.

For every result report the scope, environment, commands, relevant pass/failure counts, mutation classifications and known limitations. Fix confirmed product defects with regression tests; do not lower assertions or hide failures. Coverage remains a diagnostic metric rather than the sole acceptance criterion.

The runner now also measures tools, packaging and Wiki hooks, excluding Wiki test files from reports. For checkpoint 21, 11 Wiki unit tests ran separately in the existing Wiki environment; their branch coverage data was placed in the same output directory before the runner combined reports. The standard Python runner alone does not execute those Wiki tests, so repeat this extra step for comparable future measurements. Checkpoint 22 also ran the existing Wiki link checker against a temporary built site (6,312 local links, zero errors) and merged that separate coverage. Repeat the same checker or report its measured contribution separately when comparing later checkpoints. A full run establishes the expanded baseline; compare historical progress only on the same original file set.

A static scan of Python identifiers after the five verified removals produced 51 candidates for manual review; it is not a dead-code verdict. Dynamic lookup, public API compatibility, generated code and consumers outside this repository require further investigation before changes.

The existing API server also has 31 static unused-import findings both before and after this cleanup. These are candidates, not confirmed dead code; imports may be exposed to external callers.
